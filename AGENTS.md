# AGENTS.md — To-Do List

Постоянные инструкции для AI coding agents. Подробные требования находятся в `PROJECT_BRIEF.md`, текущее состояние — в `MEMORY.md`, специализированные процедуры — в `.agents/skills/`.

## Источники и разрешение конфликтов

1. Текущая явная инструкция пользователя управляет текущей задачей.
2. `PROJECT_BRIEF.md` — источник требований и утверждённых решений.
3. Реальные файлы, конфигурация и результаты команд подтверждают текущее состояние реализации.
4. `MEMORY.md` — краткая сводка и журнал; он может устареть и не заменяет проверку проекта.
5. `docs/architecture.md` и `docs/design-system.md` уточняют соответствующие области, когда существуют.
6. Skills задают процедуры, но не могут отменять источники выше.

При конфликте остановись, укажи источники и предложи минимальное решение. Не расширяй функциональность без разрешения.

## Начало значимой задачи

- Прочитай `MEMORY.md` и сверь важные сведения с реальными файлами.
- Открой только релевантные разделы `PROJECT_BRIEF.md` и профильные документы. Не перечитывай весь проект для локальной правки.
- Подтверди, автоматически ли среда загрузила `AGENTS.md`; если нет — сообщи, что прочитал его вручную.

## Утверждённые архитектурные рельсы

Следуй разделам 3–4 `PROJECT_BRIEF.md`: ITCSS + BEM для CSS; MVC-lite + Repository для JavaScript; HTML5, CSS3, Vanilla JS, ES Modules, `localStorage`; Playwright E2E. Не меняй структуру, зависимости или методологии самостоятельно. При конкретной технической проблеме предложи минимальную поправку и дождись согласования.

## Рабочий цикл и границы

Для значимой задачи: **Analyze → Plan → Execute → Test → Review → Document**. Используется одна модель, без субагентов и имитации параллельной команды.

Если задача помечена READ-ONLY, не создавай, не редактируй и не удаляй файлы; не устанавливай пакеты; не запускай команды с побочными эффектами; не выполняй Git/deploy-действия. Только анализируй и готовь план.

Git, GitHub, commit/push и публикацию выполняет пользователь, если отдельно не поручит обратное.

Не выдавай запланированную или запущенную проверку за успешную. При повторении одной и той же ошибки дважды остановись, изучи вывод и причину, при необходимости обратись к официальной документации, затем предложи исправление. Не ослабляй тесты только ради зелёного результата.

## MEMORY.md

`MEMORY.md` — не второй brief, а краткая память о фактическом состоянии.

- Сверяй её с репозиторием перед значимой задачей.
- После значимой итерации вызови `project-memory-maintenance`, если skill доступна; иначе следуй её `SKILL.md` вручную.
- Обнови актуальную сводку и добавь датированную запись обычно из 3–5 содержательных пунктов: результат, изменённые файлы, решения, проверки, проблемы/следующий шаг.
- Исторические записи не переписывай и не удаляй; не создавай формальные записи после пустых/незначительных итераций.
- `[DONE]` ставь только после фактической проверки. Непройденное фиксируй как `[PARTIAL]` или `[BLOCKED]`.
- Если пункт уже реализован, сначала проверь код/тесты, затем отметь `[SKIPPED/DONE]`.
- Не выдумывай файлы, функции, версии или результаты. На READ-ONLY этапе `MEMORY.md` не изменяй.

## Agent Skills

Skills — не субагенты, а подключаемые по необходимости процедуры в `.agents/skills/<name>/SKILL.md`.

- `project-memory-maintenance` — после значимой итерации или перед передачей контекста.
- `ui-ux-review` — при изменении или аудите интерфейса/CSS.
- `playwright-e2e` — при создании, запуске или отладке E2E-тестов.

Не загружай все skills заранее. Используй только подходящую. Если автоматическое обнаружение не подтверждено, прочитай нужный `SKILL.md` вручную и укажи fallback. Не создавай новую skill без повторяемого отдельного процесса.

## Качество

Пиши читаемый поддерживаемый код уровня Junior/Middle. Соблюдай проектные требования по HTML/CSS/JS и UI/accessibility из `PROJECT_BRIEF.md`. Сохраняй полезные существующие комментарии. Любое отклонение от утверждённых решений объясняй и согласовывай.
