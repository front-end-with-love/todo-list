## 1. Цель проекта

Создать небольшой, аккуратный русскоязычный веб-сайт «Список задач» (To-Do List), который выполняет исходное тестовое задание и демонстрирует грамотную организацию разработки с помощью AI-инструмента.

Приложение работает без backend. Код должен быть понятным разработчику уровня Junior/Middle: без академического усложнения, но с определённой архитектурой, ясными границами ответственности и предсказуемым потоком данных.

**Главный принцип:** простота реализации не означает монолитность исходного кода. Не объединять независимые области ответственности в один файл ради уменьшения количества файлов. Не дробить код на файлы, у которых нет самостоятельной роли.

## 2. Исходные функциональные требования

В проекте реализовать ровно четыре пользовательские функции:

1. **Добавление новых задач.** Пользователь вводит текст и добавляет задачу в список.
2. **Отметка выполненных задач.** Пользователь может отметить задачу выполненной и тем же контролом вернуть её в активное состояние.
3. **Удаление задач.** Пользователь может удалить конкретную задачу.
4. **Сохранение задач после обновления страницы.** После перезагрузки ранее созданные задачи и их статусы должны восстановиться.

Интерфейс — на русском языке. Дизайн должен быть аккуратным, адаптивным и соответствовать визуальному направлению приложенного референса.

### 2.1. Границы функциональности

Не добавлять функции, которых нет в исходном задании:

- регистрацию, авторизацию и профили;
- серверную часть, API и базу данных;
- синхронизацию между устройствами и пользователями;
- категории, теги, проекты и приоритеты;
- сроки, напоминания и календарь;
- редактирование уже созданной задачи;
- фильтры, поиск, сортировку и аналитику;
- пользовательские настройки темы;
- иные пользовательские функции, не требуемые четырьмя пунктами ТЗ.

Пустое состояние, проверка пустого ввода, понятные подписи элементов, обработка ошибок хранилища, доступность и адаптивность — требования к качеству реализации, а не расширение функциональности.

Не вводить дополнительные ограничения на содержание задачи (например, запрет повторяющихся названий или произвольный лимит длины), если они не нужны для технической безопасности.

| Логика | Vanilla JavaScript с нативными ES Modules |

| Среда Node.js | `v22.23.5` — фактическая версия окружения реализации (обновлена с `v22.23.4` security-патчем); совместимость с `@playwright/test@1.65.0` подтверждена прогоном |

### 3.1. Почему выбраны эти архитектурные ориентиры

**CSS: ITCSS + BEM.** ITCSS задаёт порядок слоёв — от общих настроек и базовых правил к конкретным компонентам. BEM отвечает за предсказуемое именование независимых блоков, элементов и модификаторов. Эти подходы дополняют друг друга: ITCSS — организация слоёв и каскада, BEM — именование и границы CSS-компонентов.

Используется практический набор слоёв ITCSS:

1. Settings — дизайн-токены.
2. Generic — reset и общие низкоуровневые правила.
3. Elements — базовое оформление HTML-элементов.
4. Objects — общие layout-паттерны и композиция страницы.
5. Components — конкретные UI-компоненты.

Слои Tools и Trumps/Utilities не создавать заранее: Tools не нужен без препроцессора, mixins и генерируемых CSS-функций; Utilities добавлять только при появлении реальных повторно используемых utility-классов.

**JavaScript: MVC-lite + Repository adapter.** Это облегчённая прикладная реализация разделения Model / View / Controller, без MVC-фреймворка, роутера, event bus или глобального менеджера состояния. Репозиторий изолирует детали localStorage от остальных модулей.

Это не попытка внедрить полную корпоративную архитектуру. Для проекта с одной функциональной областью используется одна feature-группа `tasks` и небольшое количество модулей с заранее определёнными контрактами.

### 3.2. Не использовать

- React, Vue и другие UI-фреймворки;
- TypeScript;
- Sass/SCSS/Less;
- Vite, Webpack и другие сборщики;
- runtime-библиотеки для состояния и управления DOM;
- backend, базу данных, API и авторизацию;
- менеджеры состояния, событийные шины, DI-контейнеры и дополнительные архитектурные слои;
- дополнительные зависимости без конкретного обоснования;
- внешние CDN и скрипты загрузки шрифтов: шрифт хранится в репозитории и подключается локально.

`package.json` нужен для команд разработки и зависимостей тестирования. Наличие `package.json` не означает, что приложение должно собираться или иметь runtime-зависимости.

Для запуска Playwright приложение должно открываться через локальный HTTP-сервер, а не через `file://`. Допустимо использовать одну небольшую devDependency для статического сервера, если в окружении нет уже доступного подходящего инструмента. Не создавать собственный серверный фреймворк.

### 4.1. Общие правила архитектуры

- Каждый модуль имеет одну чётко описанную ответственность.
- Зависимости направлены в одну сторону; циклических импортов нет.
- Domain/model не зависит от DOM, CSS, `localStorage`, Playwright или сетевых API.
- View отвечает только за отображение и доступ к DOM.
- Controller связывает пользовательские события, модель, репозиторий и view.
- Repository отвечает только за постоянное хранение и проверку загруженных данных.
- `app.js` — composition root: точка входа, которая запускает приложение и связывает его части. В нём нет реализации бизнес-операций и DOM-рендеринга.
- Не создавать файл на каждую отдельную функцию.
- Не создавать пустые папки и абстрактные модули «на будущее».
- Не создавать папки `helpers`, `utils`, `services`, `constants` и подобные без конкретного обоснования.
- Не переносить код между файлами только ради формального соблюдения шаблона.
- Если агент видит объективную проблему утверждённой схемы, он описывает её и предлагает минимальное изменение. Самостоятельно менять структуру нельзя.

| `components/buttons.css` | Components | Варианты кнопок, размеры, визуальные состояния и focus |

### 4.3. JavaScript-модули и назначение

| Файл | Роль | Ответственность |
|---|---|---|
| `js/app.js` | Composition root | Инициализация приложения и запуск controller; без бизнес-логики и рендеринга |
| `js/tasks/task-model.js` | Model | Модель задачи и чистые операции над массивом задач: создание, добавление, переключение статуса и удаление; без DOM и хранения |
| `js/tasks/task-view.js` | View | Получение нужных DOM-узлов, клонирование `<template>`, отрисовка списка и пустого состояния, сообщения для пользователя; без изменения модели и localStorage |
| `js/tasks/task-controller.js` | Controller | Обработка событий формы и списка, владение текущим состоянием приложения, координация model / view / repository |
| `js/tasks/task-repository.js` | Persistence adapter / Repository | Чтение, проверка, сериализация и запись данных в `localStorage`; прямой доступ к `localStorage` разрешён только здесь |

**MVC-lite — осознанно облегчённая реализация.** Controller хранит текущий массив задач в памяти и управляет потоком приложения. Model предоставляет чистые функции преобразования данных. Не добавлять подписки Observer, глобальное реактивное состояние или собственную систему событий.

### 4.4. Направление зависимостей и поток данных

Допустимые зависимости:

- `app.js` → `task-controller.js`;
- `task-controller.js` → `task-model.js`, `task-view.js`, `task-repository.js`;
- `task-model.js` не импортирует другие модули приложения;
- `task-view.js` не импортирует model или repository;
- `task-repository.js` не импортирует model, view или controller.

Поток пользовательской операции:

1. Controller получает событие от формы или списка.
2. Controller вызывает чистую функцию Model и получает новое состояние.
3. Controller обновляет своё текущее состояние.
4. Controller вызывает Repository для сохранения.
5. Controller передаёт состояние в View для отображения.
6. Если сохранение не удалось, View показывает понятное сообщение; состояние текущей сессии остаётся доступным, но нельзя утверждать, что оно сохранено для следующего открытия.

При запуске: Repository загружает и валидирует данные → Controller принимает начальное состояние → View отображает список.

Порядок обновления, отображения и сообщения об ошибке должен быть определён в плане агента и одинаково применяться во всех обработчиках.

## 5. HTML и структура интерфейса

`index.html` — единственный HTML-файл приложения.

В нём размещаются семантическая структура страницы, таблицы стилей в порядке ITCSS, `<script type="module">` и HTML-шаблон повторяющегося элемента задачи через `<template>`. Разметка задачи не должна храниться в JS-строках.

Предусмотреть:

- основную область приложения;
- заголовок;
- форму добавления задачи;
- видимую или программно связанную подпись поля ввода;
- кнопку добавления;
- контейнер списка задач;
- пустое состояние;
- `<template>` для элемента задачи;
- нативный checkbox для статуса;
- кнопку удаления с доступным названием.

Использовать семантические `main`, `header`, `form`, `label`, `input`, `button`, `ul` и `li` там, где они подходят. Не делать интерактивными обычные `div`.

## 6. CSS и дизайн-система

Дизайн-система — небольшая, но структурированная система правил и токенов, а не UI-фреймворк. Она должна отражать визуальный язык референса и применяться последовательно.

### 6.1. Design tokens — `css/settings/tokens.css`

Централизовать:

- цветовые токены и семантические роли;
- семейство шрифта и типографическую шкалу;
- line-height;
- основную шкалу spacing;
- ширины/ограничения контента;
- радиусы;
- границы;
- тени;
- размеры контролов;
- параметры focus и disabled-состояний.

Не дублировать системные значения внутри компонентов. Не создавать токен для каждого единичного значения, если оно не является частью повторяемой системы.

### 6.2. Правила типографики и композиции

Это проектные UI/UX-правила. Их следует использовать как исходные ориентиры и проверять на реальном контенте, а не трактовать как физические законы или абсолютные ограничения.

1. **Длина строки.** Для длинного читаемого текста стремиться к 60–75 знакам с пробелами в строке. Измерять фактическую меру текста, а не задавать ширину как 60–70% экрана. Диапазон применять к абзацам и длинным описаниям, а не к коротким подписям, кнопкам или строке задачи. На резиновом интерфейсе использовать ограничение максимальной меры и адаптивную ширину.
2. **Интерлиньяж.** Для обычного текстового набора ориентир — 1.4–1.5 от кегля. Для длинного чтения стремиться примерно к 1.5. Крупные заголовки и короткие UI-строки могут быть плотнее (ориентировочно 1.0–1.25), если сохраняются читаемость и визуальная цельность. В текущей реализации: 1.5 для текста, 1.2 для кнопок, 1.15 для `h1`; ниже 1.15 не опускаться — в русском наборе клипуются «Д», «Щ», «р».
3. **Кегль и гарнитуры.** Базовый текст — около 16 CSS px. Заголовки — от 20 CSS px, с иерархией по значимости. Использовать не более трёх семейств гарнитур; для этого проекта предпочтительно одно семейство и несколько начертаний. Основное выравнивание — влево. Центрировать можно короткие заголовки/сообщения не длиннее пяти строк; длинные текстовые блоки оставлять выровненными влево. Не использовать выравнивание по ширине на резиновых экранах. В текущей реализации используются одна гарнитура — Inter 4.1, подключённая локально из `fonts/` (SIL OFL 1.1, внешних запросов нет), — начертания 400 / 500 / 600 (700 не используется) и шкала кеглей 12 / 14 / 16 / 28 px (заголовка второго уровня в интерфейсе нет — единственный заголовок `h1`). Отрицательный трекинг применяется только к крупному заголовку (`h1`, −0.02em); на основном тексте 16 px и на кириллических прописных он не применяется, потому что снижает разборчивость. Набор подключённых начертаний должен совпадать с токенами весов: при отсутствии нужного начертания браузер подставляет ближайшее и дизайн незаметно меняется.
4. **Spacing.** Базовый ритм — 8 CSS px; основные опорные шаги — 8 / 16 / 32 / 64 px. Промежуточные кратные 8 значения допустимы, если нужны композиции. Шаг 4 px допустим только для тонкой внутренней подгонки, иконок и компактных контролов. Отступы между крупными группами обычно больше внутренних отступов компонентов. Не заполнять пустое пространство декоративными элементами без функции.
5. **Иерархия и воздух.** Заголовок должен быть визуально ближе к содержимому, которое он вводит, чем к предыдущей секции. Предпочтительный стартовый ориентир проекта: пространства над заголовком примерно в 2–3 раза больше, чем под ним. Это визуальная эвристика, а не математическое требование для каждого заголовка; корректировать по композиции, плотности иерархии и реальному контенту. В одном контексте интерфейса должна быть понятная визуальная доминанта и основное действие.
6. **Сканирование и композиция.** Не проектировать интерфейс механически «по F», «по Z» или по диаграмме Гутенберга. F-pattern — наблюдаемый в части задач и текстовых страниц паттерн сканирования; Z-pattern — композиционная эвристика для некоторых простых экранов; диаграмма Гутенберга описывает предполагаемую траекторию чтения при достаточно равномерном распределении однородной информации. Это разные модели и не универсальные законы поведения. Выбирать композицию по содержанию, иерархии, задаче пользователя и реальной визуальной заметности элементов.
7. **Контраст.** Для соответствия WCAG 2.2 AA текст обычного размера должен иметь контраст не ниже 4.5:1, крупный текст — не ниже 3:1. Не оценивать контраст визуально «на глаз» — проверять пары foreground/background инструментом. Избегание чистой пары `#000000` / `#FFFFFF` для длинного чтения — возможное эстетическое решение, но не требование WCAG; любые смягчённые оттенки всё равно должны пройти проверку контраста.
8. **Тёмная тема.** В текущий объём не входит. Не создавать тёмную тему или переключатель темы. Значения вроде фона `#121212` и белого текста с opacity 87% / 60% / 38% относятся к определённым рекомендациям Material для тёмной темы, а не являются универсальным стандартом. Не переносить их в светлую тему. Если тёмная тема когда-либо будет добавлена отдельной задачей, её нужно проектировать как самостоятельную палитру и проверять контраст.
9. **Цели нажатия.** Для основных интерактивных контролов целиться минимум в 44×44 CSS px, особенно для чекбокса и кнопки удаления на мобильном экране. Это более строгая проектная цель, чем WCAG 2.2 AA 2.5.8 (24×24 CSS px с исключениями), и соответствует порогу WCAG 2.2 AAA 2.5.5 (44×44 CSS px с исключениями). Не путать CSS px с Android dp: 48 dp — рекомендация для Android-интерфейсов, а не автоматический эквивалент для веба. Между соседними небольшими целями стремиться к заметному зазору, ориентир — 8 px. В каждом компактном контексте — одна визуально главная кнопка; текст действия должен начинаться с понятного глагола («Добавить», «Удалить»).
10. **Когнитивная нагрузка и карусели.** Правило «7±2» не является лимитом количества пунктов меню и не должно использоваться для искусственного сокращения/расширения элементов. Закон Теслера не означает, что сложность можно устранить: её можно распределить между интерфейсом и системой; наша задача — не переносить ненужную сложность на пользователя. Карусель в приложении не нужна. В других интерфейсах не использовать автопрокрутку и не помещать единственный экземпляр обязательной информации только внутрь карусели.

### 6.3. Применение правил к этому приложению

- Интерфейс светлый, согласно референсу. Тёмная тема не разрабатывается.
- Подпись поля ввода оформляется микро-лейблом: прописными, 12 px, начертание 600, нормальный трекинг. Текст в DOM не меняется, доступное имя поля остаётся прежним.
- Основной текст и название задачи должны легко читаться; длинные задачи должны переноситься без обрезания и горизонтального скролла.
- Основная кнопка — действие добавления задачи. Удаление визуально вторично и не должно конкурировать с основным действием.
- Чекбокс и удаление должны иметь доступные имена и удобные зоны нажатия.
- Отступы и размеры берутся из общей шкалы, а не подбираются случайно для каждого селектора.
- В пустом состоянии достаточно понятного сообщения; не добавлять иллюстрации, баннеры, метрики и рекламоподобные элементы без функции.
- Для короткого интерфейса не нужно искусственно ограничивать каждую строку 60–75 знаками: правило применяется там, где есть длинный набор.

- начертание 600 вместо 700 у `h1`;

лежит в репозитории (`fonts/`), нарезан на сабсеты, подключается с `font-display: swap`,
метрически согласованным системным fallback и preload; сторонних запросов нет.

## 8. Композиция интерфейса и UI/UX

Создать компактный одностраничный интерфейс на основе визуального языка референса.

Обязательные части:

- заголовок приложения;
- поле ввода новой задачи;
- кнопка добавления;
- список задач;
- контрол статуса у каждой задачи;
- кнопка удаления у каждой задачи;
- пустое состояние, когда задач нет.

Композицию, размеры, отступы, радиусы, состояния элементов и точную раскладку агент должен описать на этапе анализа и затем реализовать строго в пределах UI/UX-правил раздела 6. Не добавлять боковую навигацию, панели статистики, фильтры или декоративные блоки, не связанные с задачей.

Адаптивность — обязательное требование качества. Проверить узкий экран и десктоп, отсутствие горизонтального переполнения, читаемость и удобство нажатия. Не привязывать layout к проценту ширины экрана вместо ограничения меры текста и размеров контейнера.

## 9. Доступность и безопасность отображения

- обеспечить управление клавиатурой;
- сделать `:focus-visible` различимым;
- не полагаться только на цвет для обозначения выполнения;
- обеспечить контраст текста по WCAG 2.2 AA;
- для ключевых интерактивных элементов целиться в зону 44×44 CSS px;
- дать интерактивным контролам доступные имена;
- связать поле с `label`;
- отображать пользовательский текст через `textContent`, не вставляя его как HTML;
- не использовать `innerHTML` для вывода пользовательского текста;
- не допускать кликабельных `div` вместо нативных элементов управления;
- проверить масштабирование текста до 200% без потери содержимого или функциональности;
- проверить отсутствие горизонтального скролла на узком viewport.

## 10. Автоматизированное тестирование

Использовать Playwright Test (`@playwright/test`). Тесты расположить в `tests/e2e/tasks.spec.js`, конфигурацию — в корне проекта `playwright.config.js`.

### 10.1. Минимальный набор E2E-сценариев

1. Приложение загружается без ошибок.
2. Пустая задача не добавляется.
3. Пользователь может добавить задачу.
4. Пользователь может добавить несколько задач.
5. Пользователь может отметить задачу выполненной.
6. Пользователь может вернуть задачу в активное состояние.
7. Удаление удаляет только выбранную задачу.
8. Список и статусы сохраняются после перезагрузки страницы.
9. Пустое состояние отображается, когда задач нет.
10. Повреждённые или несовместимые сохранённые данные не приводят к падению приложения.
11. Узкий экран не вызывает горизонтального переполнения; основные контролы доступны.
12. Основные действия доступны с клавиатуры, фокус видим.

Тесты должны очищать изолированное хранилище перед каждым независимым сценарием. Persistence-тест отдельно проверяет reload без предварительной очистки между действием и перезагрузкой.

Изоляция достигается новым `BrowserContext` на каждый тест (поведение Playwright по умолчанию): `localStorage` пуст без дополнительных `clear()`, поэтому достаточно одного перехода на страницу.

Использовать устойчивые локаторы по ролям, доступным именам и назначению элементов. Не привязывать тесты к внутренней структуре CSS сильнее, чем это необходимо.

На старте достаточно Chromium. Дополнительные браузеры не подключать без конкретной причины.

### 10.2. Зависимости и запуск

`@playwright/test` — devDependency. Для локального HTTP-сервера допустима одна небольшая devDependency (например, `http-server`), если агент не найдёт уже доступный и воспроизводимый вариант. Не использовать Vite или другой сборщик.

`playwright.config.js` должен запускать локальный сервер через `webServer`, задавать `baseURL`, тестовую директорию и разумные параметры ожидания. Команды npm должны быть описаны в README.

Версии выбраны по официальной документации и проверены установкой: `@playwright/test@1.65.0`, `http-server@14.1.1`; совместимость с Node.js `v22.23.5` подтверждена прогоном E2E. Устанавливать зависимости допустимо только на этапе реализации, не на этапе анализа.

### `MEMORY.md`

Файл оперативной памяти проекта — краткая актуальная сводка состояния и последовательный журнал значимых рабочих итераций. Он не является заменой исходного ТЗ, `AGENTS.md` или документации архитектуры.

Разделы `MEMORY.md`:

1. **Current State** — текущий этап, фактическая готовность, последний подтверждённый результат.
2. **Approved Decisions** — только важные согласованные решения со ссылками на основной документ, без копирования его содержимого.
3. **Known Issues / Risks** — выявленные проблемы, ограничения и открытые вопросы с фактическим статусом.
4. **Next Step** — ближайшее согласованное действие.
5. **Work Log** — хронологический журнал завершённых или заблокированных итераций.

Правила ведения:

- При первоначальной инициализации изучить реальные файлы, конфигурацию, зависимости и текущее состояние. Не описывать несуществующие модули и не выдавать целевую архитектуру за уже реализованную.
- Перед значимой задачей сверять `MEMORY.md` с фактическим состоянием репозитория. Память может устареть и не заменяет проверку кода.
- После каждой значимой рабочей итерации обновлять краткую сводку и добавлять датированную запись, обычно из 3–5 содержательных пунктов: изменённые файлы, принятые решения, результаты проверок, найденные проблемы и следующий шаг.
- Не переписывать и не удалять исторические записи. Актуальную сводку можно корректировать; `Work Log` ведётся добавлением новых записей.
- Не создавать формальные записи после каждого сообщения или незначительного изменения без результата. Не добавлять пустые пункты ради количества.
- Отмечать задачу как `[DONE]` только после проверки фактического результата. Если тесты не пройдены или проверка невозможна, использовать `[BLOCKED]` / `[PARTIAL]` и указать точное состояние.
- Если запланированный пункт уже выполнен, сначала подтвердить это по реальному коду или тестам и только затем отметить `[SKIPPED/DONE]`.
- Не хранить в `MEMORY.md` длинные инструкции, полные листинги кода, историю всего диалога или дубли архитектурной документации.
- Во время READ-ONLY этапа запрещено изменять `MEMORY.md`; агент только читает его и указывает обнаруженные расхождения в отчёте.

### Agent Skills — `.agents/skills/`

Используется переносимый формат Agent Skills. Каждая skill — отдельная директория с обязательным файлом `SKILL.md`, YAML frontmatter (`name`, `description`) и инструкциями в Markdown.

В проекте предусмотрены только три узкие skill:

| Skill | Когда применять | Назначение |
|---|---|---|
| `project-memory-maintenance` | После завершения значимой рабочей итерации или перед передачей контекста | Проверить факты и корректно обновить `MEMORY.md` |
| `ui-ux-review` | При создании, изменении или аудите HTML/CSS и визуальных состояний | Проверить UI/UX, ITCSS, BEM, типографику, spacing, контраст, клавиатуру и адаптивность |
| `playwright-e2e` | При создании, запуске или отладке Playwright E2E-тестов | Поддерживать изоляцию сценариев, корректные локаторы и проверку пользовательских требований |

Skills — это подключаемые по необходимости инструкции для одной модели, а не субагенты и не отдельные процессы. Не загружать все skills без причины. Выбирать skill по описанию и задаче; в FreeBuff при наличии соответствующего инструмента использовать `skill`, а в остальных совместимых средах — их штатный механизм загрузки. Если автоматическое обнаружение не подтверждено, явно прочитать нужный `SKILL.md` и сообщить, что использован ручной fallback.

Не создавать отдельный корневой `SKILLS.md`: стандарт Agent Skills использует каталог skill с файлом `SKILL.md` внутри каждой skill. Новые skills создавать только при появлении повторяемого специализированного процесса, который не должен постоянно занимать контекст `AGENTS.md`.

**Переносимость:** проект использует `.agents/skills/` как общий путь для FreeBuff и совместимых инструментов. Если конкретная версия/сборка агента не обнаруживает этот путь автоматически, проверить её официальную документацию и настроить штатный путь без дублирования одних и тех же skills в нескольких папках.

## 12. Проверка готовности

Проект можно считать завершённым только после выполнения всех условий:

- реализованы четыре функции исходного ТЗ;
- данные восстанавливаются после перезагрузки;
- интерфейс на русском языке;
- CSS следует ITCSS-порядку и использует BEM-именования;
- JS следует MVC-lite-разделению ответственности и использует отдельный Repository для `localStorage`;
- зависимости не образуют циклов;
- `localStorage` не используется вне Repository;
- дизайн-токены централизованы;
- UI/UX-правила из раздела 6 учтены, а объективные отклонения объяснены;
- пользовательский текст безопасно выводится в DOM;
- есть адаптивная версия и базовая клавиатурная доступность;
- контраст и зоны нажатия проверены;
- Playwright E2E-тесты выполнены, результаты зафиксированы;
- README, `docs/architecture.md` и `docs/design-system.md` соответствуют фактической реализации;
- `AGENTS.md` содержит актуальные стабильные инструкции и не дублирует спецификацию;
- `MEMORY.md` отражает проверенное состояние проекта и не выдаёт план за реализацию;
- проектные skills находятся в `.agents/skills/<name>/SKILL.md`, имеют корректные метаданные и применяются по назначению;
- в консоли нет необработанных ошибок в основных сценариях.

**Фактический статус:** условия выполнены в реализации от 2026-11-13; результаты прогонов и число сценариев — в `MEMORY.md`.

Не заявлять, что тесты пройдены, пока они фактически не запущены и не завершились успешно.

## 13. Границы ответственности AI-агента

- На первом этапе — только READ-ONLY анализ и подготовка плана.
- Не создавать и не изменять файлы до отдельного разрешения пользователя.
- Не устанавливать зависимости на этапе анализа.
- Не выполнять Git-команды и не настраивать GitHub/хостинг.
- Не запускать субагентов: используется одна модель.
- Не добавлять функциональность за пределами ТЗ.
- Не менять утверждённые методологии ITCSS, BEM и MVC-lite без конкретного технического обоснования и отдельного согласования.
- Не трактовать UI/UX-эвристики как жёсткие WCAG-нормы; обязательные нормативные критерии и проектные ориентиры должны быть помечены раздельно.
- Перед значимой задачей сверять актуальную память с реальным состоянием проекта; читать профильную документацию по необходимости, а не механически все файлы перед каждым изменением.
- После каждого значимого этапа давать фактический отчёт: что сделано, какие файлы затронуты, что проверено, какие проблемы остались.
- После подтверждённой значимой итерации обновлять `MEMORY.md` по правилам раздела 11; для этого использовать `project-memory-maintenance`, если skill доступна.
- Использовать `ui-ux-review` и `playwright-e2e` только для соответствующих задач. Не создавать дополнительные skills без повторяемой необходимости.
