# Архитектура

Приложение — небольшое модульное frontend-приложение: MVC-lite для прикладной
логики, Repository для хранения, ITCSS + BEM для стилей. Без фреймворков,
сборщика и глобального состояния.

## Роли модулей

| Файл | Роль | Ответственность |
| --- | --- | --- |
| `js/app.js` | Composition root | Создаёт View и Repository, передаёт их Controller, вызывает `controller.init()`. Без бизнес-логики и рендеринга |
| `js/tasks/task-model.js` | Model | Чистые операции над массивом задач: `createTask`, `addTask`, `toggleTask`, `deleteTask`, `findTaskIndex`. Без DOM, CSS и хранилища |
| `js/tasks/task-view.js` | View | Кеширует узлы при создании, клонирует `<template>`, рисует список и пустое состояние, показывает сообщения, управляет фокусом, предоставляет подписки на события |
| `js/tasks/task-controller.js` | Controller | Владеет текущим состоянием, обрабатывает события формы и списка, вызывает Model и Repository, передаёт состояние в View |
| `js/tasks/task-repository.js` | Repository | Единственное место доступа к `localStorage`: чтение, валидация, сериализация, запись; наружу отдаёт результат-объект |

## Направление зависимостей

```text
js/app.js
  ├── js/tasks/task-controller.js
  ├── js/tasks/task-view.js
  └── js/tasks/task-repository.js

js/tasks/task-controller.js
  └── js/tasks/task-model.js

js/tasks/task-model.js        → нет импортов приложения
js/tasks/task-view.js         → нет импортов приложения
js/tasks/task-repository.js   → нет импортов приложения
```

Controller импортирует только Model; View и Repository приходят аргументами из
composition root. Циклических зависимостей нет. Коды ошибок Repository в View
передаются строкой и превращаются в текст внутри View — Controller не импортирует
Repository ради констант.

## Поток данных

**Запуск.** `app.js` создаёт View (сразу кеширует узлы) и Repository, передаёт их
Controller. `controller.init()` загружает состояние через `repository.load()`,
подписывается на события View и выполняет первый `render`.

**Жизненный цикл списка.** Элемент `<ul id="task-list">` есть в DOM только пока
есть задачи. View создаёт его при первом рендере с непустым списком и удаляет
из документа, как только задач не осталось; в разметке (`index.html`) его нет,
поэтому при загрузке страницы без задач в дереве документа списка нет вообще —
только пустое состояние. Разметка самой строки задачи при этом остаётся в
`<template>`, а не в JS-строках.

События `change` и `click` View подписывает не на список, а на постоянный
контейнер `#task-list-container`: список создаётся и удаляется, а делегирование
от контейнера работает в обоих случаях. Строки для восстановления фокуса
View тоже ищет в контейнере, а не в списке.

**Добавление.** `submit` формы (Enter или кнопка) → `preventDefault` → значение
обрезается по краям. Пустая строка или отсутствие `crypto.randomUUID()` → сообщение,
фокус в поле, состояние не меняется. Иначе `createTask(text, crypto.randomUUID())`
→ `addTask` → `repository.save` → очистка поля → `render` → явный `view.focusInput()`.
Фокус возвращается в поле при любом исходе и не зависит от поведения браузера.

**Переключение статуса.** `change` чекбокса → `toggleTask` → `save` → `render` с
восстановлением фокуса на чекбоксе той же задачи по `data-task-id`.

**Удаление.** `click` по кнопке → индекс удаляемой задачи запоминается до изменения
списка → `deleteTask` → `save` → `render`. Фокус: задача с индексом
`min(удалённый, длина − 1)` — то есть следующая, а если удалена последняя, то
предыдущая; при пустом списке — поле ввода.

**Ошибка записи.** Состояние в памяти не откатывается, список остаётся рабочим,
View показывает сообщение; данные могут не пережить перезагрузку.

## Хранилище

Ключ `todo-list.tasks.v1`, значение — `{"version":1,"tasks":[{"id","text","completed"}]}`.

`load()` возвращает `{ tasks, error }`, `save(tasks)` — `{ ok, error }`; исключения
наружу не выходят. Коды ошибок: `unavailable` (нет доступа к хранилищу), `corrupt`
(данные не разобраны, несовместимая версия, невалидные записи или дубликаты ID),
`write-failed` (запись отклонена). При частичном повреждении валидные записи
сохраняются в памяти, невалидные и дубликаты отбрасываются. При запуске хранилище
не перезаписывается: запись происходит только при явном действии пользователя.
Значение несовместимой версии не мигрируется.

## CSS: ITCSS и BEM

Слои подключаются в `index.html` отдельными `<link>` в порядке каскада:

1. Settings — `fonts.css` (`@font-face` локально подключённого Inter) и `tokens.css`
   (цвета, типографика, spacing, радиусы, границы, тени, размеры, focus).
2. Generic — `reset.css` (box-sizing, минимальная нормализация, `[hidden]`).
3. Elements — `base.css` (типографика документа: `body`, `h1`, `p`).
4. Objects — `app-layout.css` (центрирование, контейнер, вертикальный ритм, адаптивность).
5. Components — `buttons.css`, `form-controls.css`, `task-form.css`, `task-list.css`, `task-item.css`.

Файлы шрифта лежат в `fonts/` (`inter-{400,500,600}-{cyrillic,latin}.woff2` и `OFL.txt`
с лицензией SIL OFL 1.1) и подключаются локально: в `index.html` стоят `preload` для трёх
кириллических сабсетов, внешних запросов и CDN нет.

Слои Tools и Trumps не создавались: препроцессора нет, utility-классы не понадобились.
BEM: блоки `app-layout`, `task-form`, `task-list`, `task-item`, `button`, `text-field`,
`checkbox`; элементы через `__`, модификаторы через `--` (`task-item--completed`,
`button--primary`, `button--icon`). Стили не опираются на вложенность тегов вне
своего блока.

## Когда добавлять модуль

Новый модуль оправдан, если у него есть самостоятельная ответственность и
собственный контракт, а не просто группа функций. Для текущего объёма (четыре
функции, одна feature-область `tasks`) пять JS-файлов достаточны: разделение
дальше дробило бы код без пользы.
